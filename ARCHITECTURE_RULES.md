# Serron Architecture Guardrails (Baseline)

1) Single entrypoint
- Приложение запускается только через `mobile-app/app-entry.js`.
- Ни один модуль не запускает приложение сам по себе.

2) Runtime feature registry
- Каждая новая фича обязана зарегистрироваться в `runtime-registry` до инициализации.
- Расширение функционала — только через реестр, не прямой вызов инициализации.

3) UI: single source of truth
- Верхнеуровневые UI-элементы создаются только в HTML.
- JS не создаёт/не клонирует/не удаляет верхнеуровневые блоки.
- Один feature — один UI-контейнер, без дублей.

4) Границы фич
- Talk, Calendar, Feed, Services, Profile, Storage и др. — отдельные features.
- Каждый отвечает только за свою область, без прямых обращений “внутрь” чужого feature (только публичный интерфейс).

5) Запрещено
- MutationObserver “для починки”.
- Периодические таймеры-чистильщики.
- Дедупликация DOM как стратегия.

6) Service Worker
- Dev: SW выключен (unregister) и не перехватывает запросы.
- Prod: только versioned SW с очисткой старых кэшей.

7) Однократная инициализация
- Каждый feature инициализируется один раз.
- Повторный запуск не создаёт второй UI/листенер/composer.
- Нет скрытых авто-подключений “всех файлов в папке”.

8) Структура проекта
- Чёткие зоны: features, shared/common, bootstrap/app-shell, assets/static, archived/old.
- Нет двух файлов с одинаковой ролью (например, “state.js” в разных местах).

9) Проверка перед добавлением фичи
- Регистрируется ли фича в реестре?
- Не создаёт ли она UI поверх HTML-контейнеров?
- Не лезет ли в чужие фичи напрямую?
Если “да” на три вопроса — можно писать код.
